# 证据驱动排错

用户报告是待验证假设；“现象存在”“执行机制”和“真实根因”是不同结论。

## 选择模式

- 只描述问题，或要求检查、分析、定位、规划：调查，不改实现或 Git 状态。
- 明确要求修复或按方案执行：先查实，再修改；不得沿用旧任务授权扩大范围。
- 可运行隔离临时目录中的诊断。会重导入、生成或保存工程文件的工具，先确认授权与必要性，并保留运行前后的差异。

## 找到负责边界

1. 固定实际与期望行为、触发步骤、版本、对象 ID；检查相关本地修改。
2. 从可观察入口追踪：负责对象 → 生效的数据/配置 → 调用与状态变化 → 失败条件 → 结果。
3. 优先用现有日志、测试和可控复现区分假设。根因有歧义时检查能改变结论的竞争解释，不为凑步骤枚举无关假设。
4. 证据不闭环时，明确已确认事实、支持性推断和缺口，不把合理解释写成定论。

搜索命中不能证明运行时执行，截图通常不能证明根因；无文本引用也不能排除序列化、事件、反射和动态加载。

涉及 Unity 资源、UI、生命周期或构建差异时，按问题类别读取 [Unity 核查表](references/unity.md)，不加载无关类别。

## 获准后的修复

- 编辑前简述已确认根因与最小修改边界；证据推翻原假设时，不实施针对错误假设的修复。
- 在拥有错误行为的位置修复，保护用户修改，不顺手重构或手改生成物。
- 用原触发条件回归，再检查共享路径。窄修复做聚焦测试；状态、协议或主流程改动扩大验证。
- 检查最终 diff，区分本次修改、既有修改和工具产物。构建成功不等于运行或视觉验收。

## 交付与停止

默认只给结论、关键证据、修复或下一步、验证缺口；复杂问题再展开因果链，不固定报告章节数。
写明是否修改。关键证据不可得时停止并请求最少必要信息；不要用推测补齐根因。
