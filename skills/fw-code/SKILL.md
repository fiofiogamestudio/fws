# FWC 工程维护

FWC 是代码仓库；新安装默认目录为 `fwc/`，既有 `fw/` 或显式相对路径按宿主配置与真实登记定位，不机械替换目录名。`fw.toml`、`Fw.*` 命名空间、Godot 的 `res://scripts/_fw/fw` 投影与生成协议保持稳定；顶层 `fw` 是项目管理入口，不等于 FWC 的物理安装目录。

## 先确定真实目标

- 确认 Git 根和本次维护的是框架自身还是宿主游戏；从实际文件、宿主配置和 submodule 信息定位框架，不拼接固定 cwd。
- 框架自身：读取其仓库根下 `docs/rule.md`、`docs/spec.md`。
- 宿主游戏：读取宿主根下 `docs/fw/rule.md`、`docs/fw/spec.md`；需要操作命令时再读对应 `use.md`。
- 读取 `fw.toml [runtime].game`，缺省按 C#。确认客户端运行时与已启用 Kit；生成器使用 .NET 不代表游戏需要 C#，修改配置字段不等于完成语言迁移。
- 无法定位关键规范时先查工程入口并说明缺口，不能套用另一个工程的结构。

## 修改合同

1. 区分规则、结构、操作和实现。长期规则只在用户明确要求时更改；结构变化更新 spec，操作变化更新 use。
2. 按该工程的权威链分工：C# 模式使用 Godot 表现、C# core 和 bridge；GDScript 模式使用 GD 玩法 system/规则对象与 context 意图入口。两者都遵守 config 与 system 注册合同，不让视图或编辑器拥有玩法真值，也不为纯 GD 工程重新引入 C# bridge。
3. 宿主内容留在宿主；通用能力才进入框架。FWC 不强依赖 FWE、FWA 或 FWS。
4. 修改 schema 或生成来源后运行对应生成，不手改 `_gen`、`_fw` 投影或打包配置。
5. 框架规范和模板从 FWC 的源文档派生；宿主文档不得反向覆盖框架。此技能由 FWS 维护，不复制一套核心规范。

## 按风险验证

- 文档修改：核对链接及适用模板镜像，不一律启动引擎。
- 宿主改动：使用宿主的生成、构建、测试和相关运行验收；框架自测不能替代宿主验证。
- 框架运行时、生成器或模板改动：在实际框架根运行 `tools/test.ps1` 或 `tools/test.sh`，并按受影响合同补聚焦测试。
- 保持工程声明的 Godot/.NET 基线，不为通过验证顺带升级环境。实际构建、运行、视觉结果和未验证部分分别报告。
- 纯 GD / Web 改动需用标准 Godot 检查并实际验证导出后的配置包、交互与所需持久化；导出成功不能代替浏览器运行验收。未启用或尚不支持的 Kit 不默认补成第二套语言实现。
