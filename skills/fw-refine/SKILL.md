# 打磨已有成果

改善用户要的成果，不把开放式优化变成无限扩展或追逐分数。

## 模式与范围

- 分析、评分、规划：只读。优化、改好、按方案执行：可以实施范围内改进。
- “继续”继承上一轮范围、量表与剩余问题，不自动扩大权限；没有新证据时先复核停止条件。
- 从实际成果、用户目标和已有记录建立基线，保留原架构、受众与约束；不凭描述推断质量。

## 按复杂度工作

小范围评估默认给结论、最强证据和改进建议，不强制加权表格或长报告。
明确要求分数、满分或持续多轮打磨时，先读 [评分规则](references/scoring.md)，建立量表后再改，后续保持可比较。

1. 检查入口、直接负责内容和最相关验证，找出影响目标的实际缺口。
2. 按收益选择一组协调改进：先核心阻碍，再高频错误、维护成本，最后低风险体验；不为形式补功能。
3. 疑似 Bug 先查实触发条件和负责边界，再决定是否修复；不要让“优化”掩盖根因未知。
4. 获准后实施最小有价值批次，保护无关修改，沿用项目规范和必要生成流程。
5. 用风险相称的验证复评；没有有效结果不能加分，构建、运行和视觉证据分别报告。

调查只扩展到可能改变结论或优先级的部分；继续搜索不再有决策价值时，记录未知并停止。

## 停止与交付

达到目标、没有高收益改进、收益低于成本/回归风险，或下一步需要新的产品决策、权限或关键证据时停止。
不要为“满分”无限循环，也不要把暂时没发现问题说成绝对完美。

默认输出结论、优先问题、实际修改（只读时省略）、验证及下一步；严重问题不可省略。
区分本轮运行、当前静态、历史产物和未验证项，事实、推断与主观评价不要混写。
多轮任务保留一行交接：范围与版本｜量表｜当前分/可信度｜已验证/未知｜下一步或停止理由。
