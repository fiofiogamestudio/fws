# 按意图提交

一个提交解决一个原因，代码与直接配套测试、配置可以一起提交。

## 确定边界

- 先确认真实仓库根、分支，以及 staged、unstaged、untracked；已有暂存不是默认授权。
- 只问状态、评估或审查：只读报告；明确要求提交：可以整理并提交当前预期修改。
- 提交不等于修复或推送授权；额外修改、push、PR 和历史重写分别需要用户要求。
- 保留无关修改与本机证据；不提交凭据、缓存或来源不明的生成产物。

## 整理与提交

1. 分开阅读暂存区和工作区 diff，检查未跟踪文件及最近提交风格。遇到 submodule，分别查看内外仓库状态。
2. 按修改原因分组，不按文件类型机械拆分；一个修复及其回归测试应能一起审查、一起撤销。
3. 简述拟提交内容。单组用一句话，多组用列表或小表；已有明确提交授权且归属清楚时直接继续，歧义部分留下询问。
4. 按精确路径暂存；混合意图文件仅在可以可靠拆分时按 hunk 暂存。每组核对 cached diff，再提交。
5. 沿用仓库语言和前缀；无约定时用 `feat / fix / refactor / docs / test / chore`，标题写清实际意图，不用笼统的 update。
6. 每次提交后检查 HEAD、剩余修改和验证结果，确认没有夹带文件。

## 易错边界

- 不使用全量暂存、`commit -a`、`reset --hard` 或覆盖式 checkout 整理混杂工作区。
- 生成物先确认来源；Unity 资产与 `.meta` 保持配对。
- 不在脏仓库上擅自 merge/rebase。非快进或分支不明时先报告，不强推。
- 跨 submodule 发布时，先验证并发布组件，再提交宿主引用；不要交付他人无法获取的 gitlink。

## 交付

简述提交 hash 与意图、仍保留的修改、实际验证范围；只有真实完成推送才写“已推送”。
