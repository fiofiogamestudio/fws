# 深度盘点与收敛

目标是解释工程的大部分占用并找齐有依据的候选，不是追求删除比例。几百 GiB 工程只找到几 GiB 并非必然错误，但必须说明剩余的大头具体是什么、为何保留或还缺什么证据。不能用“可能有用”覆盖一个混合大目录而停止。

## 一次全树扫描，多轮离线下钻

Windows 大工程使用 `scan-space-native.ps1 -Root <绝对工程根> -Progress`；跨平台使用 `scan-space.mjs --root <绝对工程根> --inventory --json --progress`。把 stdout 存到工程外临时 JSON，stderr 保持进度。扫描不跳过 ignored、隐藏目录、嵌套工程或 `.git`，但不跟随链接。原始数据不是删除计划。原生版要求 Windows PowerShell 5.1+，无 npm 依赖；账本和副本比较工具要求 Node.js 20.10+。

`inventory` 每行包含 `relativePath`、`parentRelativePath`、递归 `logicalBytes/files`、直属 `directBytes/directFiles`、`childDirectories`、递归和直属 `errorCount/skippedCount`、修改时间范围。所有直属量之和等于已测总量；父递归量等于直属量加直接子目录递归量。旧式 `directories` 和 `largestFiles` 仍是有上限的展示榜，不能求和当总量。

```powershell
node <skill-directory>/scripts/review-space.mjs --scan <inventory.json> --limit 60
node <skill-directory>/scripts/review-space.mjs --scan <inventory.json> --focus output --chunk-mib 256
node <skill-directory>/scripts/review-space.mjs --scan <inventory.json> --decisions <decisions.json> --json
```

`--focus` 是 inventory 中的相对目录；`--chunk-mib` 默认 1024，仅控制把大子树拆到多细，没有固定深度上限。每轮优先检查最大未查明项，必要时继续聚焦、更小分块或枚举其直属大文件。`--limit` 只限制文本显示，末尾仍报余项数/容量，JSON 保留全部。`scope=tree` 表示整个子树；`scope=direct` 仅表示该目录直属文件集合，**绝不能把 direct 行的目录路径直接当递归删除目标**。审批删除前逐个枚举所选精确文件或另行确认完整子树。

`partitionCoveragePercent=100` 只证明已测文件都入账；`reviewedPercent` 才表示已有用途判定的字节比例。`unmeasured.logicalBytes=null` 表示错误/跳过路径大小未知；不以零估算，不承诺物理可回收容量。不同时间扫描要说明变动；比较算法版本优先复用同一 snapshot。

大 inventory 用 Node 工具解析，不在 Windows PowerShell 5.1 中反复 `ConvertFrom-Json` 整棵目录账。先完成一次扫描再做定向内容比较，避免多路全树扫描和大文件哈希争用同一磁盘。复扫未完成时保留其未完成状态；实际清理可按已实时封存的精确目标核对前后数量及卷空闲变化，不把旧工程总量冒充本轮前后测量。

同目录里混有可清理文件和保留文件时，加 `-FileDetails`（原生）或 `--file-details`（Node，自动启用 inventory）获取 `directFileEntries`。可只对已定位的热点子树重新扫描，按该子树自己的总量审查，不能与旧的全工程快照重复相加。大型工程默认仅保留目录量，需要全工程逐文件决策时再开启明细，避免无谓生成庞大 JSON。

逐文件决策使用 `scope: "file"` 和文件相对路径；必须能在对应快照的 `directFileEntries` 中找到，字节数取自快照而非人工填写。同一目录下未单列的文件仍在 `direct` 余量中，行上的 `excludedFiles` 列出已单独记账的文件。支持把数 GiB 的重复文件列为条件候选、把同目录内几 KiB 的差异源码或 DLL 保留；不能因此递归删除目录。文件、direct 和 tree 决策之间也不能重叠。

## 查明大头，不把风险目录整体丢出清单

对每个主要家族查生成者 → 当前消费者 → 必须保留的最小集合 → 可清理的精确兄弟项。先用 `rg --files --hidden`、定向 `rg` 和 Git 状态查源码/配置/清单；不要直接在海量二进制里全文搜索。搜索不到引用不证明无消费者，目录旧或 ignored 也不证明可删。

目录名会误导两次：`Library` 中可能放了手工验证工程，验证工程内又可能藏着普通旧 Player。遇到这类混合目录，应穿过外层保留目录继续检查内层构建，分别保留源码/收据、审查运行 payload。Unity 的 `ArtifactDB`、`SourceAssetDB` 及锁文件也不会出现在纯“子缓存目录”榜单中；可在完整工程与版本/依赖、编辑器归属均核实后逐文件评估，不能因为已检查 Artifacts/Bee 就漏掉所有直属文件。

| 大头 | 应做的拆分与证据 |
|---|---|
| `Library` / `.godot` / `node_modules` / `bin` / `obj` | 区分引擎缓存、工具手工工程、外部依赖、嵌套仓库和验证证据；检查版本/锁文件/生成入口以及运行时直接加载的二进制。嵌套验证工程的源码保留，内部缓存仍可单独评估。 |
| `output` / `.local` / 历史导出与构建 | 查打包命令、`latest`/构建状态/交付清单、服务器静态根和当前客户端入口。旧工作副本里的新增/不同源码单独保留；已有新版本不自动使所有旧包可删。按版本、平台、任务批次逐层拆分。 |
| 截图、录像、中间帧、转码与播放器副本 | 区分原录屏、已采用成片、批注/对比基线、可重建中间帧、重复拷贝。查录制及转码入口、审阅链接与发布凭据。确认中间输入可从保留材料重建，再列候选；“可以重新录一次”不保证重现原始证据。 |
| Rec/回放/验证输出 | 查 preset、ReplaySet、continuation、初态与相邻 manifest/result 的消费链，保护整套必需文件及它们引用的后续输入；不因几个回放输入位于 output 就保留全部历史播放器。 |
| 备份、压缩包、克隆副本 | 先比文件清单/大小，再按可能重复的组做按需内容哈希或归档目录比较；不全盘无差别哈希。Git 状态、独有文件、不同版本、当前交付、外部引用必须分别检查。哈希相同只证明内容相同，不证明路径可删除。 |
| `.git`、gitdir、bare repo | 可以解释占用，但保留仓库对象与历史；不得把改名存放的 Git 元数据当缓存，不自动 prune/gc 或删除工作树。 |

“条件候选”要具体说明缺少哪条事实：关闭对应进程、确认保留哪一版、验证某生成入口、确认唯一媒体是否归档。对能从本机源码/清单核实的事实继续查，不把所有判断推给用户。待确认项不进入默认 BAT。

### 旧生成产物的退役，不等同于重复文件

分别审查两条依据：**可重建/相同副本**靠保留材料与恢复过程；**已退役生成产物**靠生成入口、任务完成或后继替代、当前消费者检查、原地保留的成果凭据及明确退役影响。后者不要求能逐字节重建每个过时测试 EXE，但不能用来删除独有源码、原始素材、仍需复现的基线或唯一成果。日期旧、文件名含 old、搜索零命中都不足以单独证明退役。

历史测试报告、build receipt 和媒体来源收据记载旧路径，并不自动代表程序当前仍加载该路径。区分生成时读取、完成后查看、重新导出和历史复现四种用途；沿实际代码与交付入口查清。已有后继也不自动授权删除前版：确认保留现役版本/基线及历史成果，说明清退后旧程序无法直接运行，只有不再承担必需用途的生成 payload 才能进入计划。根目录混有收据、测试 XML、日志时原地保留这些文件，单独选择 Data/运行库/EXE；不能只把证据搬到临时目录就删除整个版本。

审查账用 `retired` 单列这一类，不能为了纳入候选伪填“重新构建可还原历史版本”。需要 `retirement.generatedBy`、`completionEvidence`（非空数组）、`consumerAudit`、`preservedEvidence`（非空数组）、`impact` 和执行前置条件，公共 reason/evidence 仍必填。它与可再生成项一样拒绝未知错误/跳过量，且不会自动产生删除计划。保留依赖需要换成等价副本时，先验证内容与消费者、保存原路径到保留副本的恢复映射，再检查所有计划间的依赖，不能悄悄删除上一批承诺保留的唯一恢复来源。

### 用户指定旧实验的保留标准

默认保护独有原图、录屏和历史对比。若用户明确表示某批已否决或已替代的旧视觉实验“只保留游戏素材”，应把这个选择应用到所问批次，重新审查此前仅因唯一媒体而保留的项；不能继续机械保留，也不能扩大到所有工程文件。先记录用户选择、实验完成/替代证据和当前消费入口，再按文件角色区分实际游戏资产、可采用源素材、源码/配置、当前交付，以及已退役的截图/原始帧/中间视频。

只将确认不承担当前用途、且属于用户选定退役范围的媒体列为精确目标；同目录的游戏素材、源码、回放输入、当前交付和不明文件继续保留。说明独有实验媒体将无法精确恢复、旧报告的相应图链会失效，保留实验结论与清理记录。不能伪称这些独有截图是缓存或可逐字节重建，也不能用该选择删除正在进行的实验或作为上一轮恢复依赖的唯一副本；后者仍须先核对并更新保留链。

### 历史副本的定向比较

大头来自多个历史工程/资源副本时，用 [compare-trees.mjs](../scripts/compare-trees.mjs) 比较已经选定的旧副本和明确保留的对应目录：

```powershell
node <skill-directory>/scripts/compare-trees.mjs --candidate <old-copy-absolute-dir> --retain <kept-copy-absolute-dir> --json --progress
```

它只读取两棵互不重叠的真实目录，不跟随链接，不写入文件。先按相对路径和大小筛选，仅对同路径同大小文件读内容计算 SHA-256；哈希前后复查元数据。完整结果区分内容一致、不同、仅旧副本存在和无法判断，另列仅保留副本存在的文件。文本 Top N 之外的余量仍计入报告。

优先比较最大的几个资源/工作副本，不对整个盘做内容哈希。内容一致只是证据：还要核对该副本是否正被加载、整个工作副本能否重建、保留副本是否确实保留，以及恢复时如何还原路径。不同、独有、变化中和无法读取的文件不能按重复文件规则删除；旧生成二进制可另走上面的退役审查，独有源码和成果仍保护。不能以“多数相同”删除整个副本，没有证据就明确保留或待查，不编造大额候选。

`PackageCache` 等含数万小文件的副本先按 inventory 的包级容量选根，例如分别比较一个完整 Burst 包，不先把两个缓存全集串行遍历完才给首个结果。Unity 版本、manifest、lock 文件及包描述相同只用于筛选，不能替代整包内容核对；不同包保留，不用部分相同文件拼成残缺安装包。根缓存若被生成的 csproj、校验脚本或当前工作直接读取，应保留其原路径；历史副本即使整包相同，也要记录从保留包恢复到原路径的映射、把保留包加入依赖集合，并检查历史 worker 和编译进程。进程归属不明时继续列出容量和缺失条件，归为 conditional，不把它漏出清单，也不执行删除。

历史诊断播放器可能由“复制完整基线，再替换 DLL/PDB”产生。查构建收据和实际文件映射；若每个文件都能由保留基线或保留替换文件按 SHA-256 精确恢复，且已无当前运行用途，可把整个诊断副本列入候选。记录恢复步骤，并把基线、替换文件及其构建凭据加入保留集合；`*-csc`、`compile` 等目录此时是恢复依赖，不能又被另一组缓存清理选中。合并多组计划时交叉检查所有目标与保留依赖，执行前重查保留依赖仍在且未变化。

### 跨目录与改名副本

同相对路径比较找不到“工作区 capture.mp4 → delivery/gameplay.mp4”或不同阶段改名复制的截图。使用 [find-duplicates.mjs](../scripts/find-duplicates.mjs) 在两个或更多明确、互不重叠的目录范围内按内容查找，先按文件长度分桶，只对有匹配可能的文件流式计算完整 SHA-256：

```powershell
node <skill>/scripts/find-duplicates.mjs --root <selected-output-dir> --root <selected-local-dir> --suffix .png,.mp4 --min-bytes 1048576 --json --progress
```

大工程优先复用 native `-FileDetails` 快照：从已选范围按类型/大小筛选，生成绝对文件路径的 JSON 数组，再传 `--files-json <list.json>`。此模式只检查名单与祖先，不重复遍历全树；输出明确其覆盖范围只是名单，不能声称根目录所有文件均已查明。默认内容读取并发 2，可设 `--concurrency 1` 避免磁盘争用；不要同时跑几路大树哈希/扫描。

工具复查路径、文件身份和哈希前后元数据，拒绝根重叠/重定向；把硬链接别名作为一个文件身份，变化、跳过、无法读取和未核实硬链接另列。每组展示全部成员、SHA-256 和理论重复逻辑量，不自动挑选保留者，不生成删除计划，也不保证物理可回收量。只有大小相同、部分内容相同或画面相似都不算确认重复。

内容相同之后继续查路径的角色。前后两阶段截图即使一样，也可能分别证明不同测试阶段；保留对应结果/清单并记录阶段到保留图的映射。旧消费者重跑需要原路径时写明恢复步骤；当前运行入口仍需要该路径的则保留。多轮清理要把恢复链改为最终仍在的副本，复核所有旧依赖并持久记录转接，不能删掉上一轮承诺保留的唯一恢复源。

录制目录可进一步拆分成功合成后的编码输入与成片。只有生成代码确实使用无重编码的流复制、成功收据及现存成片哈希/轨道/帧数相符、没有后续消费者直接使用中间输入时，才可选择对应的编码视频和音频输入，保留成片、片段成片、收据及语义回放源。记录从成片拆流恢复的方法与容器字节可能不同的边界；失败/取消录制中的唯一恢复媒体、原始 PCM/WAV 与有损 AAC 不能按这一规则当作等价副本。

片段成片也可能是完全重复副本，但需另行核实：导出已经成功完成、确为单段、导出根成片与该片段逐字节 SHA-256 相同、当前消费者使用根成片，且保留录制与合成两类收据以及原片段路径到根成片的恢复映射。全部成立后才可精确选择该片段副本；不能推广到多段导出、失败导出或仅画面看起来相同的视频。跨轮曾承诺保留的片段也需先完成等价依赖替换审查，不能直接删除。

## 可选审查决策账

记录本次来源审查，供合计与二次复核使用。必须绑定扫描根和 `finishedAt`，重新扫描后重新核对；它不会转换成清理 manifest。

```json
{
  "schemaVersion": 1,
  "root": "D:/Projects/ExampleGame",
  "scanFinishedAt": "2026-10-25T00:00:00.000Z",
  "decisions": [
    {
      "relativePath": "Library/Artifacts",
      "scope": "tree",
      "disposition": "conditional",
      "reason": "已核对为导入缓存，但对应 Unity 仍运行",
      "evidence": ["ProjectSettings/ProjectVersion.txt", "当前进程项目路径", "已检查目标内部无手工源文件或独有证据"],
      "regenerate": "使用保留的 Assets、Packages 与工程配置重新导入，可能耗时较长",
      "prerequisites": ["关闭对应工程的 Unity Editor 后重查"]
    }
  ]
}
```

分类为 `regenerable`（重建证据已确认）、`retired`（生成产物退役依据已确认）、`conditional`（具体条件未满足）、`keep`（应保留）；未覆盖项自动为 `unreviewed`。每项要有原因和证据；前两类分别记录重建方式或退役事实，候选均记录前置条件。条目不能重叠；混合目录应拆细或启用文件明细，不能给父目录“可删”再以子目录“保留”当例外。路径提示完全不计入已审查容量。错误或跳过未消除的子树不能列为已确认可再生成或已退役。

## 迭代评价与停止条件

每轮记录：总字节/文件数、可再生成、已退役生成产物、条件候选、应保留、未查明、未测量，以及本轮新增候选、纠正的误判和下一轮最大问题。工具回归通过不代表工程用途审查完成；大额未查明家族还在时，不能因实现验收完成就宣称已达到深度清理的收敛条件。

- **完整度**：已测字节与文件数的非重叠账必须全部对齐，展示之外的余量必须显式保留。首次榜单不等于完成。
- **粒度**：所有单项 ≥1 GiB 或 ≥工程总量 1% 的未查明组都要继续下钻、查来源，或留下无法继续的具体阻碍；小工程相应缩小阈值。大量同类小项按生成规则合并审查，不能被 Top N 漏掉。
- **保留理由质量**：主要混合目录不能只因“有证据/有源码”整体标记保留。对大 `keep` 家族也复查，剥离嵌套缓存；保留单项需指向当前输入、唯一资产、发布/审阅凭据或源码事实。
- **安全性**：已知保护集（源码及 meta/uid、dirty/staged 文件、当前交付、回放初态、唯一媒体、Git、链接范围外内容）不能出现在候选中。用隔离混合目录测试和独立复核检查误报；不能在真实工程试删来评估技能。
- **收益**：后续一轮已覆盖剩余最大问题，仍无新增有证据候选、无未处理大额模糊保留项、无已知安全缺陷，才停止。遇到必须由用户决定的唯一版本/媒体用途时明确保留并列条件，不虚称“已经彻底清干净”或无限循环。

交付时把发现的逻辑容量、已封存目标和实际删除容量分开。本技能优化/只读评估任务不要求生成真实删除 BAT，更不授权运行它。
